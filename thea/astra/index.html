Thea: Towards the Harness of Embodied Agents

Revisited after GPT-6 Astra

HAI Lab · Eastern Institute of Technology, Ningbo

Abstract. Thea brought the coding-agent harness to the physical world by supplying a persistent readable world state and verifiable action outcomes. With GPT-6 Astra operating a robot SDK inside a coding environment, we revisit tool granularity and ask which harness components come from the model, the coding harness, or the physical-world layer.

Revisiting the Tools

Astribot S1 · Left parallel gripper

Direct SDK control

We gave GPT-6 Astra, running in Codex, the Astribot S1 Python SDK and its documentation. Using the left parallel gripper, the agent attempted four tasks: tabletop cleanup, cleanup after a base approach, drawer retrieval and closure, and loaded transfer.

The agent registered head-camera RGB-D observations in the base frame, solved inverse kinematics against the SDK’s forward kinematics, screened joint samples for self-collision, and issued one motion segment at a time. Base movement used velocity pulses gated by lidar clearance.

The first errors were geometric and were corrected during execution. All four tasks reached the final states shown below, illustrating the control code the model can construct for these particular tasks.

Revisiting the Harness

Model · coding harness · physical-world layer

Codex supplied the agent loop, tool execution, files and the write–run–read–fix cycle. We read the experiments through four physical-world mechanisms: keeping track of the world, checking action outcomes, understanding the body, and retaining useful procedures.

World state and memory

The 18 navigation runs are grouped into Astra, instructed scene-graph memory, and navigation-evaluation conditions, with three runs per condition in each dataset. Each replay pairs the saved observations with that run’s observable agent events; completed and incomplete runs are both retained.

In graph-memory runs, the agent wrote room and route records to files and consulted them during navigation. These records are estimates maintained within the current run. Read the replay together with the context stream and Workspace to follow new observations, route choices and later revisits. Completion labels follow the recorded run outcome, including its stopping criterion.

Outcome checking

The Revo2 cup-lift trials ask whether reaching a motion target means that the object was actually lifted. A useful outcome check must inspect the cup and its support after the motion.

In the cup-rim trials, the wrist rose about 7.58 mm while the cup stayed on its support. The agent inspected post-action images, rejected unsuccessful lifts and adjusted its grasp. These were task-specific visual checks whose accuracy was not independently measured.

Body limits and safety

After the Revo2 hand was installed, the existing collision model still described the parallel gripper. The experiment compares observed hand-surface landmarks with calibrated model projections to expose this geometry mismatch.

Human-prompted geometry checks gave local per-finger RMS errors of 1.35–2.20 mm at a fixed hand shape. After slight closure, overall RMS error was 5.26 mm and the maximum was 9.57 mm. Calibration at one hand shape did not guarantee the same geometric accuracy after the fingers moved.

Workspace

Skills and reusable files

We examine reusable code as part of the agent’s working memory. Every navigation run above exposes its saved final Workspace, so readers can inspect the procedures and state files produced during that run.

Open a run’s Workspace to inspect its navigation helpers, task scripts and, where present, scene_graph.json. A helper script preserves a procedure; a scene graph preserves discovered world state. The provided, modified and new labels distinguish the initial interface from files left by the run. These snapshots document navigation, rather than the separate code reuse across the four robot tasks.

03

What Changes and What Remains

Across these demonstrations, the model wrote control code while the coding harness supplied the execution loop and files. The runs still had to re-sense the world, check what their actions achieved and work within the body’s limits. The observations motivate the following responsibilities for a physical-world harness.

01

Tool granularity blurs downward

The model can write motion segments directly against the SDK, so the model–tool line is no longer fixed.

02

The Embodiment Profile does more work

Kinematic limits, workspace and calibration become explicit when they are no longer hidden inside a policy.

03

Safety moves into the harness

Lower-level commands require heavier workspace bounds, collision checks and force limits.

04

Evaluation precedes physical-world self-improvement

Robot experience cannot become a reliable signal until the physical world has an equivalent of exit codes and unit tests.
